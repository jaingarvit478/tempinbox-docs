A missing verification email is not proof of a disposable-domain block or a TempInbox outage. Check the submitted address, form result, selected inbox, sender queue, and delivery status.

## Diagnose the failed step

| Observed result | Next check |
| --- | --- |
| Form rejects the address | Validation message and accepted-address policy |
| Form accepts it but no email is queued | Account creation and send-trigger logs in your own application |
| Send is attempted but rejected | Bounce or transport status and exact recipient |
| Message is delayed or not visible | Queue status, selected inbox, and receiving-service evidence |
| Message arrives but code fails | Expiry, recipient account, code reuse, and resend behavior |

If you cannot inspect the sender's logs, use its supported resend or support flow without assuming the cause. Delivery timing is not guaranteed.

## Why do sites reject temporary addresses?

Sites may apply disposable-domain lists or other rules for account abuse prevention and durable contact. A domain-level block checks the part after @. Creating a different address prefix on the same domain does not fix it.

Use an address type accepted by the site. For an account you intend to keep, choose a durable mailbox or accepted alias. When testing your own application, configure and inspect its policy deliberately in the test environment.

## Lost inbox access

Use the same browser profile where the inbox was created. Private browsing, another profile, or cleared site data may not have the saved access token. The address alone does not restore access, and there is no supported cross-device recovery.

## Self-hosted implementation debugging

For an instance you operate, use its deployment configuration and current server logs to inspect authentication, Turnstile requirements, rate limits, and delivery. The [implementation reference](/api-reference/overview) is separate from the hosted browser workflow. Do not export hosted browser credentials as a substitute for a supported automation integration.
